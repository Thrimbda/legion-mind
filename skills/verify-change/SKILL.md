# verify-change

为已有改动提供比例化、可复查的验证证据。不要用模型自信、Agent 共识或测试名称代替实际执行结果。

## 默认方法

1. 从用户目标、改动和风险提取需要证明的行为。
2. 选择成本最低但证明力足够的直接检查；优先覆盖改动路径、失败路径和容易出现的反例。
3. 记录实际命令或工具、关键参数、退出状态和有用结果。区分源代码推断、测试结果、运行时观察与外部系统事实。
4. 明确失败、跳过、环境限制、残余风险和会使结论失效的条件。
5. 只在检查真实支持时声明通过；证据不足时写清当前可证明范围。

普通工程验证直接使用以上方法。只有主张依赖专门领域方法、外部权威、延后观测或价值判断时，才读取并使用 `references/REF_COGNITIVE_VERIFICATION.md`。

## 输出

默认在回复中给出验收映射、检查结果、未验证内容和结论。用户要求持久报告时写入其指定位置或仓库既有测试报告位置；不要求任务台账、固定文件名或交接 schema。
